## 0. Resumen en una línea

La app se **re-arquitecturó** del wizard monolítico `enroll` al modelo **solicitudes-app**
(`applicant → checklist → /me/* → pago diferido debt`). Todo en la rama
**`feature/fase-3-applicant`**; `flutter analyze` limpio; **NO probado E2E en vivo**.

## 1. Flujo implementado (de punta a punta)

```
abrir app → (sesión guardada) reanuda al checklist/pago/estado
        └ o → selección → login / registro
registro:  informativa (beneficios + precio) → paso 1 (persona + privacidad →
           POST /driver-auth/register, nace applicant + token) → checklist
           (GET /me/checklist) → subir documentos + agregar vehículo
           (POST /me/{documents,vehicles} + archivos)
tras aprobación admin: pago diferido purpose='debt' + T&C (GET /me/debt para el
           monto) → "en revisión" → (pago aprobado) entra al shell
```

- **Bootstrap de sesión** (`SplashScreen` en `/`): lee token + `GET /me` y enruta por
  estado — `applicant`→checklist, `approved`→pago/shell, resto→estado. Selección pasó a
  `/selection`.
- **Enum `DriverStatus`** ganó `applicant`.
- Se **reutilizó** el UI existente: tema, `PaymentForm`/`showPaymentSheet`, `media_picker`,
  `VehicleDraftSheet`, validadores del paso 1, campos de cédula/teléfono.

## 5. ⚠️ Gotcha de infraestructura (2026-08-13)

**prod y dev comparten la MISMA base de datos** (Supabase), limitada a **15 conexiones**.
Correr **dos backends** a la vez (Railway + `npm run dev` local) agota el pool →
`EMAXCONNSESSION max clients reached` y **pantallas en blanco** en el panel. Mitigación:
correr **uno solo**. El panel local (`edv-route-admin/src/environments/environment.ts`) se
apuntó a Railway **temporalmente**; revertir a `localhost:3000` al desarrollar contra el
backend local. Fix de fondo: Supabase separado para prod.

## 6. 🐛 Fix del panel (mismo día)

El detalle de solicitud del panel (`edv-route-admin`, `features/requests/request-detail.ts`)
quedaba **en blanco**: llamaba `load()` (que lee el input requerido `id`) en el **constructor**
